1. Phase Overview

The goal of Week 5–6 was to build the core visual mechanic of Squiggle: the interactive HTML5 drawing canvas and its real-time synchronization across all players in a room via Socket.IO.

Main Objective: Ensure that when the Drawer moves their mouse, coordinates and tool data are instantly captured, rendered locally, and broadcasted globally with near-zero latency, so everyone else sees the artwork appear in real-time.

2. Features Implemented

  • ✅ HTML5 Canvas Syncing: Intercepts mouse/touch events to calculate precise X/Y coordinates relative to the canvas scale.
  • ✅ Comprehensive Tool Suite: Support for Freehand Brush, Eraser, and a dynamic Color Picker & Brush Size slider.
  • ✅ Advanced Shapes Engine: Implemented drag-to-draw geometry logic for rectangles, circles, lines, ovals, curves, arrows, and squircles.
  • ✅ Flood Fill Algorithm: A complex mathematical breadth-first search (BFS) algorithm to instantly color continuous bounded areas.
  • ✅ Latecomer Synchronization: Automatically fetches the complete canvas image and sends it to players who join mid-round so they aren't staring at a blank screen.
  • ✅ Undo / Clear Functions: Drawer can revert strokes or wipe the entire board, and those commands are instantly relayed to viewers.

3. Step-by-Step Code Walkthrough (For Beginners)

This section breaks down the most essential blocks of code we wrote this week so that anyone with zero basics can understand exactly how our canvas synchronization works.

A. The Drawing Relay (Backend)

This code lives in server/socket/drawingEvents.js. It is the absolute core of the multiplayer drawing system.

socket.on('drawing', (data) => {
    // We do NOT save 'data' to MongoDB. That would crash the database!
    
    // Instead, we instantly bounce the exact same 'data' to everyone 
    // else inside the same room (except the person who sent it).
    socket.to(data.roomId).emit('drawing', data);
});
What this means: When the drawer moves their mouse, their browser says "Hey server, I just drew a red dot at X:50, Y:100". The server immediately turns around and shouts to the whole room: "Hey everyone, the drawer just drew a red dot at X:50, Y:100!".

How it connects: We call this a "dumb relay" architecture. The server acts like a mirror. It doesn't think about the drawing, it doesn't save the drawing, it just bounces the signal to the guessers so their screens can draw the red dot at the exact same time.

B. Latecomer Synchronization (Frontend)

Since the server doesn't save the drawing, how does a player who joins late see what was already drawn? This code in DrawingCanvas.jsx solves that.

// 1. The latecomer asks the server for the current picture
socket.emit('requestCanvasState', { roomId });

// 2. The server asks the CURRENT DRAWER for the picture
socket.on('getCanvasState', () => {
  if (isDrawer && canvasRef.current) {
    // The drawer takes a literal "screenshot" of their HTML canvas
    const dataURL = canvasRef.current.toDataURL();
    
    // The drawer sends the screenshot back to the server
    socket.emit('sendCanvasState', { roomId, canvasState: dataURL });
  }
});

// 3. The server forwards the screenshot to the latecomer
socket.on('canvasStateReceived', (dataURL) => {
  // The latecomer paints the screenshot onto their blank canvas!
  const img = new Image();
  img.src = dataURL;
  img.onload = () => { ctx.drawImage(img, 0, 0); };
});
What this means: We use peer-to-peer style sharing. The server doesn't know what the picture looks like, so it asks the Drawer. The toDataURL() command converts the entire drawing into a massive string of text (Base64). That text is sent to the latecomer, who converts the text back into an image and pastes it on their screen.

How it connects: This ensures that even if you disconnect and reconnect, or join 30 seconds into a round, your screen instantly updates to match the Drawer's screen.

C. Fixing the Shape "Ghosting" Bug (Frontend)

When drawing a shape like a circle, dragging the mouse leaves a trail of hundreds of circles. Here is the fix from our useCanvas.js hook.

// 1. When you first click down, save a snapshot of the canvas
const snapshot = ctx.getImageData(0, 0, canvas.width, canvas.height);

// 2. Every time you drag the mouse by 1 pixel...
const drawShapePreview = (currentX, currentY) => {
  // WIPE the canvas completely and put the snapshot back!
  ctx.putImageData(snapshot, 0, 0);
  
  // Now, draw the NEW circle over the snapshot
  ctx.beginPath();
  ctx.arc(startX, startY, radius, 0, Math.PI * 2);
  ctx.stroke();
};
What this means: Instead of drawing 500 overlapping circles while dragging, we trick the eye. Every time you move the mouse even 1 millimeter, we instantly delete the circle you just drew by pasting the snapshot (which is the blank canvas before you clicked), and then we draw the new circle. It happens so fast (60 frames per second) that it looks like a smooth, live preview!

How it connects: We only emit the drawing to the Socket.IO server when you release the mouse button (mouseUp). This saves a massive amount of internet bandwidth.

4. Debugging & Issues Faced

Issue #1: Shape "Ghosting" During Dragging

The Problem: When a user selected the "Circle" tool and dragged their mouse, the canvas would draw hundreds of overlapping circles for every millimeter the mouse moved, creating a solid tube of ink instead of a single growing circle.

The Fix: We implemented a "Snapshot" mechanic for shapes (as explained in the code walkthrough above). On mouseDown, we save the exact state of the canvas using ctx.getImageData(). On every mouseMove, we completely wipe the canvas back to the snapshot, and draw the new shape outline. When the user releases the mouse (mouseUp), we draw the final permanent shape and emit it to the server.

Issue #2: Infinite Broadcast Loops

The Problem: Early in development, when the server broadcasted a stroke, the receiving client would draw it, but their local drawing function would mistakenly think the user drew it, causing the client to emit the stroke BACK to the server in an infinite loop.

The Fix: We strictly separated local user input from incoming socket data. The useCanvas hook only emits coordinates if the action was triggered by a physical mouse event (isDrawing = true). When socket events come in, they bypass the mouse trackers and call rendering functions directly without triggering the socket emitter.

🎓 Final Viva Preparation

1. Why don't you store the drawing history in the database?

Drawing generates massive amounts of data (often 60 coordinate pairs per second per user). Storing this in MongoDB would instantly crash the database due to rate limits and bandwidth. Socket.IO is designed for ephemeral, high-speed binary and text relay, making it the perfect tool to bounce the data without saving it.

2. How does the flood-fill (paint bucket) tool work mathematically?

The flood fill tool reads the pixel data of the HTML5 canvas using getImageData. It checks the RGBA color of the pixel you clicked. It then uses a Breadth-First Search (BFS) queue to scan all adjacent neighbors. If a neighbor matches the original clicked color, it paints it the new color and adds its neighbors to the queue. It stops when it hits a boundary of a different color.

3. What happens if two people draw at the exact same time?

Only the assigned "Drawer" is allowed to emit drawing events. The frontend canvas locks out all mouse inputs for guessers. If a hacker bypassed the frontend and sent drawing socket events anyway, we have checks in the backend to verify that socket.id === room.currentDrawer.socketId before relaying.

4. How do you handle players resizing their browser window?

The canvas is built using relative coordinates rather than absolute screen pixels. When a user draws, we calculate their mouse position as a ratio of the canvas width/height. When that data is sent to another player on a smaller screen, the ratio is multiplied by their local canvas size, ensuring the drawing scales perfectly regardless of monitor size or aspect ratio.
